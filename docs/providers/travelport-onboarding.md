# Travelport Onboarding (Live Integration)

## Purpose

Implementation-ready checklist for enabling live Travelport integration once credentials are available.

## Required environment variables

- `INTEGRATIONS_DRIVER=travelport` (or per-request `provider=travelport`)
- `SUPPLIER_CREDENTIAL_ENV=test|production`
- `SUPPLIER_TOKEN_REFRESH_BUFFER_SECONDS=300` (recommended)
- `SUPPLIER_HTTP_TIMEOUT_SECONDS=30` (recommended baseline)
- `INTEGRATIONS_USE_DATABASE_CREDENTIALS=true|false`
- `INTEGRATIONS_PERSIST_TOKENS_TO_DATABASE=true|false`

Travelport-specific:
- `TRAVELPORT_BASE_URL_TEST`
- `TRAVELPORT_BASE_URL_PRODUCTION`
- `TRAVELPORT_TOKEN_PATH`
- `TRAVELPORT_CLIENT_ID_TEST`
- `TRAVELPORT_CLIENT_SECRET_TEST`
- `TRAVELPORT_CLIENT_ID_PRODUCTION`
- `TRAVELPORT_CLIENT_SECRET_PRODUCTION`
- `TRAVELPORT_AUDIENCE` (if required by account setup)

## Config keys to verify

- `config/integrations.php`
  - `driver`, `supported_drivers`, `credential_environment`, `http_timeout_seconds`, token/db flags
- `config/travelport.php`
  - `base_url`, `token_path`, `credentials.test`, `credentials.production`
- `config/supplier_integration.php` (compatibility references if used)

## Token flow

1. `TravelportAuthService` resolves credentials via `ProviderCredentialResolver`.
2. Uses `SUPPLIER_CREDENTIAL_ENV` to select `test` or `production`.
3. Fetches token from configured token endpoint.
4. Caches token via `SupplierTokenCache`.
5. Optional DB persistence through integration token repository when enabled.
6. Uses `executeWithAuthRetry()` path for one 401 replay.

## Base URLs

- Sandbox/Test: `TRAVELPORT_BASE_URL_TEST`
- Production: `TRAVELPORT_BASE_URL_PRODUCTION`
- Token endpoint: combine base + `TRAVELPORT_TOKEN_PATH` (or full token URL in config)

## Expected scopes and headers

Headers:
- `Authorization: Bearer {token}`
- `Accept: application/json`
- `Content-Type: application/json`
- `X-Correlation-Id: {uuid}` (internal traceability requirement)

Scopes:
- Confirm exact scopes in provider portal (shopping/pricing/booking capability).
- Record granted scope list in credential handover notes.

## Test search payload example

Use internal API first (provider-specific wire format remains in adapter):

```json
{
  "origin": "KHI",
  "destination": "JED",
  "departure_date": "2026-06-01",
  "adults": 1,
  "provider": "travelport"
}
```

## Pricing/revalidation prerequisites

- Use a valid `offer_reference` generated by Travelport search.
- Preserve provider context in `opaque_context` when required by adapter.
- Revalidation must produce successful status before booking.

## Booking prerequisites

- Fresh successful revalidation snapshot required (`BookingRevalidationGuard`).
- Provide travelers in normalized format expected by booking endpoint.
- Use idempotency key for booking API requests.

## Error handling notes

- Map all provider failures to `ApiErrorData` + `SupplierIntegrationException`.
- API envelope must remain:
  - `error.code`
  - `error.message`
  - `error.supplier_code`
  - `error.correlation_id`
  - `error.http_status`
- Do not expose raw vendor payloads in controller responses.

## Rate-limit assumptions

- Unknown until contract/tenant tier confirmed by Travelport.
- Start with conservative assumptions:
  - burst-sensitive behavior
  - retry only safe/idempotent reads
  - no blind retry for booking writes

## Timeout and retry rules

- Baseline timeout: 30s (`SUPPLIER_HTTP_TIMEOUT_SECONDS`)
- Retry policy:
  - one auth replay on 401 via shared auth retry path
  - no repeated retries for booking/ticketing writes
  - optional controlled retry for search/pricing reads only if provider policy allows

## Suggested enablement sequence

1. Validate token acquisition in sandbox.
2. Enable search live path and validate normalized offers.
3. Enable pricing/revalidation and verify guard behavior.
4. Enable booking create last.
5. Repeat smoke tests in production after credentials switch.
